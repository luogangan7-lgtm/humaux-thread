# ADR-0029: Subject-scoped recall — Qdrant `subject_ids` payload + any-of prefilter + PG re-check + RESTRICTIVE subject visibility（研究问题 Q7/Q8 读侧；Card 9）

日期：2026-09-06 · 状态：Accepted · 影响面：`migrations/0155_subject_visibility_policy.{sql,manifest.toml}`（owner SECURITY DEFINER STABLE 谓词 `private.memory_subject_visibility_ok(uuid,uuid)` + `private.memory_records` 上 AS RESTRICTIVE FOR SELECT 策略 `memory_records_subject_visibility`，TO `role_gateway, role_maintenance`）/ `crates/projection/src/dense.rs`（`SUBJECT_IDS_FIELD` + `DenseQueryFilter::about_any_of`）/ `crates/adapters/src/qdrant.rs`（`IndexablePayload{payload, subject_ids}` + `with_subject_ids`，`subject_index_body`，`DenseQuery::with_subject_ids`）/ `projection_worker.rs`（`resolve_memory` 同事务读 `memory_subjects` → payload）/ `read_materialize.rs`（`final_memory_ids_about_in_txn` / `materialize_final_bodies_about_in_txn`：共享 hydrate gate 的 subject 复核）/ `retrieve.rs`（`materialize_private_read_serving_about`）/ `bins/gateway/src/{recall.rs,mcp_application.rs}` + `contracts/mcp/recall.schema.json`（`recall.search.subject_ids: [uuid]`）/ `xtask/src/rls_check.rs`（`check_subject_visibility_policy`）/ Baseline §6.1.3 / 测试：`crates/adapters/tests/{qdrant_contract,qdrant_live,projection_worker}.rs`、`bins/gateway/tests/{mcp_gateway,semantic_recall_wiring}.rs`。前置：卡 1–8 已在树上（HEAD 0c3b16b，迁移至 0154）。

## 背景
卡 8 让 memory 可以*关于* subject（`private.memory_subjects`），但只有 `memory.enumerate {subject_id}` 这一条精确谓词读得到它；语义召回（`recall.search`）的 Qdrant payload 没有 subject 字段，`projection::dense::build_dense_filter`——workspace 里唯一的查询 filter 构造点——也没有 subject 子句。「把关于这个客户的全部记忆召回来」做不到。同时 Q8 裁决的「subject policy AS RESTRICTIVE ANDed on top」还没有落地；它必须晚于 0140 的 headless 读弧并且必须**豁免** `role_retrieval_worker`，否则一行被 subject 收窄的 memory 在投影时 FAILED，整个 tenant 的 watermark 在 §15.7 下冻结。

## 决定

### D-A payload `subject_ids` + any-of 预过滤 + PG 复核（Qdrant 只是预过滤）
- **写侧**：`projection_worker::resolve_memory` 在同一事务里读 `private.memory_subjects`（`role_retrieval_worker` 自己的 SELECT，见 D-B 的豁免），`finish_row` 经 `IndexablePayload::with_subject_ids` 写入 payload 数组字段 `subject_ids`（排序去重，wire 确定性）。字段名只有一个拼写：`projection::dense::SUBJECT_IDS_FIELD`，写侧与读侧共用——拼写漂移会让 subject 召回静默返回空。集合级 `subject_index_body()` = `{"field_name":"subject_ids","field_schema":{"type":"uuid"}}`，与 `tenant_index_body` 并列，一个 family collection 一次。
  - **为什么挂在 `IndexablePayload` 而不是 `QdrantPointPayload` 字段上**：`QdrantPointPayload { .. }` 的结构体字面量散落在 `private_projection_registry.rs` / `recall_envelope_g23.rs` 等本卡不可改的测试里，加字段会让它们编译失败；而 subject 链接本来就只在索引写路径（§18.2 gate 之后）才有意义。wire 上 `subject_ids` 与其它 payload 字段并列，读侧看不出区别。
- **读侧 Qdrant**：`DenseQueryFilter::about_any_of(&[SubjectId])` 在 `dense.rs` 内把 `Or([Eq{subject_ids, id}...])` AND 到 tenant 子句与 §6.1.2 visibility 析取**之后**；消费 `self`，所以 subject-scoped filter 仍然只能先经 `build_dense_filter` 得到——§17.1 的单构造点不变，`no_handwritten_filter_scan` 依旧只放行 `dense.rs`。用 `Eq`（Qdrant `match.value` 对数组字段 = array-contains）而不是 `In`（那是多 workspace 成员测试的形状）。`DenseQuery::with_subject_ids` 是 adapter 面的包装。
- **读侧 PG**：`recall.search` 的 `subject_ids` 再传到 `retrieve::materialize_private_read_serving_about` → `read_materialize::materialize_final_bodies_about_in_txn` → `final_memory_ids_about_in_txn` 的 `EXISTS(memory_subjects … subject_id = ANY($4))`，与卡 4 的 `include_archived` 在同一个共享最终资格 gate 里（overlay 带进来的 memory 同样过这道门）。Qdrant 预过滤**永不**是权威：payload 说关于 A 但 PG 没有链接的点会被丢掉（gateway 真 Qdrant 套件有这一案）。旧签名（`materialize_private_read_serving` / `final_memory_ids_in_txn` / `materialize_final_bodies_in_txn`）保留为空 subject 的薄包装，不动 `context_repo.rs` / `continuity_read.rs` 调用点。
- **读侧 PG，overlay 一腿**：同一个 subject 范围也管 RYW overlay 能带进什么。`read_materialize::load_overlay`（唯一的 overlay 装载点）在 `subject_ids` 非空时用 `EXISTS(private.evidence_subjects … subject_id = ANY($9))` 复核每条 overlay Evidence——没有声明为「关于所请求 subject 之一」的、尚未投影的写入**不会**以 `temporary_evidence` / `artifact_unavailable` 的形式带着原始 body 回来（review P1：此前只裁剪了 `linked_memory_ids`，item 本身仍无条件推入）。真 Qdrant 套件有 A/B 两个 scope 各一次带 token 的召回作证。
- **回填（review P1）**：`subject_ids` 只在 worker（重）投影一行时写入；0155 之前投影的点没有这个字段，any-of 预过滤永远匹配不到，subject-scoped 召回会对「0155 之前就已链接的 memory」静默报空，而信封的 `truncated=false` 让调用方分不清「没有关于 A 的」和「关于 A 的都早于字段」。仓库里唯一的重投影机制是 memory 自己 stream 上的一张新票（`memory.supersede/restore/archive` 已在发的 `MEMORY_LIFECYCLE` 票）：worker 经 `ops.outbox → memory_evidence → memory_records` 解析、同事务重读 `memory_subjects`、以**同一个**确定性 point id（注册键 = memory_id + updated_at + body_sha256，链接不改这三者）覆盖 upsert。0155 的 C. 块就是 §60 `issue_stream_log_row + insert_outbox` 的集合化逐字版，由迁移 owner 一次性执行：对每个「live 注册点 + `status='active'` + 至少一条 `memory_subjects`」的 memory，按其 PRIMARY-first Evidence 发一张 `MEMORY_LIFECYCLE` 票（每 (stream, evidence) 一张）；未链接的 memory 不需要——缺失的数组字段本来就不匹配 any-of，正是「不关于任何人」。worker 结清之前是普通的投影滞后（§15.5 RYW 覆盖持 token 的调用方），不是永久的洞。manifest postcheck E. 断言每个满足条件的 memory 的 stream 上都有一张 ISSUED 的 `MEMORY_LIFECYCLE` 票；`projection_worker.rs` S3 端到端证明「投影后再链接 → 重发票 → 同一 point 改写为 `[A]` → A-scoped 查询命中」。**不选 projection_version 升版**：§15.1 的版本是 stream 身份，新版本的 stream_log 为空，仓库里没有「为新版本全量重发票」的机制，升版本身重投影不了任何东西；**不选读侧对缺字段的点放行**（`is_empty` 分不开「无字段」和「已投影但无链接的 `[]`」，要么给预过滤开洞、要么在 payload 里埋哨兵值——永久的合同疣）。
- **MCP 面**：`recall.schema.json` 增 `subject_ids: [uuid]`（`minItems 1`、`maxItems 256`——与 `BoundedSet::MAX_LEN` 同量级——`uniqueItems`）；`mcp_application::recall_search` 解析为 `Vec<SubjectId>`，畸形元素 `INVALID_INPUT`。输出 schema 不变（`output.schema.json` 是开放对象，item 形状未动）。

### D-B `memory_records` 上的 RESTRICTIVE subject 可见性（0155）
- 谓词 `private.memory_subject_visibility_ok(p_tenant_id, p_memory_id)`：`NOT EXISTS` 任一挂接 subject 对本会话不可见。LEFT JOIN `private.subjects`（本会话在 `subjects` 的 tenant policy 下看不到的行 → NULL → 不可见，fail closed），可见性经 `private.visibility_allowed('TENANT_SHARED', s.tenant_id = GUC, false, false)` 判定——**今天 subject 可见性 = 同租户**；per-subject ACL 钩子就在这一处函数体里，后续加 subject 级 visibility class 只改传给 `visibility_allowed` 的三个布尔。没有链接的 memory 恒可见（aboutness 从不*扩*读，也不*隐藏*未链接行）。
- **为什么 SECURITY DEFINER**：`memory_subjects` 自己的策略（0154）含 `EXISTS(... private.memory_records ...)`；从 `memory_records` 的策略内联子查询回 `memory_subjects` 会再次进入 `memory_records` 的策略，PostgreSQL 直接报 `infinite recursion detected in policy`。owner 定义者函数打断环：函数内以 `role_migration_owner` 重入 `memory_records`，命中 §59.1 I4 的 `current_user = 'role_migration_owner'` 布尔弧，且 RESTRICTIVE 策略的 TO 表不含 owner。STABLE、`search_path = pg_catalog`（0137 同形）、只接受行自己的 `(tenant_id, memory_id)`，无法指向别的租户。
- 策略 `memory_records_subject_visibility AS RESTRICTIVE FOR SELECT TO role_gateway, role_maintenance USING (tenant_id = current_setting('humaux.tenant_id', true)::uuid AND private.memory_subject_visibility_ok(tenant_id, memory_id))`。FOR SELECT 同时约束 UPDATE/DELETE 的行读取，所以 arbiter 操作对不可见目标依旧 `NOT_FOUND`（Q6）。**A1 headless 豁免**：retrieval / consolidation / private worker 不在 TO 表——投影必须索引它拿到的每一行，真正的按读者收窄在 Qdrant 查询时（`with_subject_ids`）和 PG hydrate gate（D-A）里、在读者自己的角色下发生。**A2 逐字 tenant 子句**在前，§48.2 四项枚举识别得到。
- 0012/0153 的 permissive 策略文本**未改**：`rls_check` 钉的 `evidence_objects_tenant_and_visibility` 哈希 `e877f26c…` 不动（0155 postcheck 断言它），**不需要重新 pin**。`rls_check` 新增 `check_subject_visibility_policy`：definer/STABLE/owner/search_path + RESTRICTIVE/SELECT-only + TO 表**恰等于** `{role_gateway, role_maintenance}` + `memory_records` 上恰一条 RESTRICTIVE 策略——把 `role_retrieval_worker` 加进 TO 表立刻红（§15.7 回归哨兵）。
- **谓词的 ACL（review P1）**：`REVOKE ALL … FROM PUBLIC; GRANT EXECUTE … TO role_gateway, role_maintenance`——与 0137/0147/0149 的 definer 函数同一纪律。策略表达式以查询角色执行，所以恰好这两个角色需要 EXECUTE；其余任何对 schema private 有 USAGE 的角色（首先是 `role_batch_issuer`，它对 `memory_subjects` / `memory_records` 都没有 SELECT）若能调用它，就能以 owner 权限逐 bit 探出「这条 memory 有没有本租户之外的 subject 链接」——正是 `memory_subjects` 的 RLS 要藏的事实。`rls_check::check_subject_visibility_policy` 与 manifest postcheck A2 都钉：PUBLIC 无 EXECUTE，八个 runtime 角色里 EXECUTE ⇔ ∈ {gateway, maintenance}；S2 测试直接以 `role_batch_issuer` 调用并断言 `42501`。
- §6.2.2 矩阵：没有新表；grant 变化只有这个新函数自己的 EXECUTE（写进 §6.2.2 的 ADR-0029 段）。

### D-C 验收（真 Qdrant，不是 unit-only）
- `crates/adapters/tests/projection_worker.rs`（fake embedder `TestDoubleProvider`，真投影 worker、真 Qdrant、真 PG）：S3 `reissued_lifecycle_ticket_reprojects_the_same_point_with_current_subject_ids`（回填机制端到端，见 D-A）；S2 末尾以 `role_batch_issuer` 调谓词得 `42501`（ACL）；两个 subject A/B、三条 memory（A-only / B-only / A+B）经 `run_once` 投影，scroll 回读 payload `subject_ids` 逐条相等；`DenseQuery::with_subject_ids(&[A])` 只返回 {A-only, A+B}，从不返回 B-only（**注错哨兵**：把 `about_any_of` 改成恒真即红，本卡实测）；USER_PRIVATE 的 A-only 行：所有者查 A 命中、同租户另一用户查 A 零命中——subject 过滤与 visibility 是 AND 不是替代。PG 侧同文件：`SET LOCAL ROLE role_gateway` 读到行；把谓词函数体换成恒 false（回滚事务内）读到零行；`role_retrieval_worker` 在两种情况下都读到全部行（§15.7 哨兵）。
- `bins/gateway/tests/mcp_gateway.rs::native_gateway_semantic_recall_real_qdrant_pg_and_ryw_acceptance`（真 gateway + 真 Qdrant + 真 PG + 进程内 retrieval-worker 的固定向量 embedding，不用 DashScope）：直接种投影点（worker-less harness）+ `memory_subjects` 行；`recall.search {subject_ids:[A]}` 返回 {A-only, A+B} 且绝不含 B-only；`{subject_ids:[B]}` 同理；一条 payload 声称 A 但 PG 无链接的点被 hydrate gate 丢弃（Qdrant 只是预过滤的证明）；未过滤的召回仍返回全部；带 `consistency_token` 的 A-scoped / B-scoped 召回各一次：声明为「关于 B」的未投影写入只在 B-scoped 里以 `temporary_evidence` 出现，无声明的写入两边都不出现（overlay 一腿）。

## 否决
- **`build_dense_filter` 加第三个参数**：会改 `sparse.rs` 与两处 `qdrant.rs` 调用（前者不在允许清单）；`about_any_of` 作为 `DenseQueryFilter` 的消费型方法达到同一个「只能在 `build_dense_filter` 之后收窄」的类型级保证。
- **`Condition::In` 做 any-of**：`match.any` 对数组字段虽然也能工作，但它是 workspace 成员测试的既有形状，读起来像标量测试；`Or(Eq...)` 明确表达「数组包含任一」。
- **在 gateway 后过滤 subject**：违反「Qdrant 只是预过滤、PG 是权威」——后过滤在 gateway 进程里，不在 RLS 快照里。
- **inline EXISTS 策略（不用 definer）**：策略环递归，PostgreSQL 直接拒绝。
- **RESTRICTIVE 策略覆盖 headless 角色**：0140 的 §15.7 冻结回归——见 D-B。

## 已知局限
- 0155 回填票与既有 `MEMORY_LIFECYCLE` 票一样绑定 Evidence，而 worker 的 `resolve_memory` 按 PRIMARY-first `LIMIT 1` 解析——一个 Evidence 蒸馏出多条 memory 时只有第一条被（重）投影。这是投影解析既有的绑定方式，不是本卡引入；改成按 memory 绑定需要给 ticket 加 memory 身份（§60 字段表），由后续 card 决定。
- subject 可见性今天只有「同租户」一个判据，所以 PG 侧的「未授权读者零行」在真实数据上只能由跨租户会话触发（已被 tenant policy 覆盖）；本卡把它做成**可注错的钩子**（谓词函数换成恒 false 即零行）并在真 Qdrant 面用 visibility 轴证明 AND 关系。加 subject 级 ACL 时只改 0155 的函数体 + 给 `visibility_allowed` 的三个布尔。
- `merged_into` 非空的 subject 仍按其自身可见性计入（没有「被合并的 subject 不再 gate」的规则）；合并语义由后续 card 定。
