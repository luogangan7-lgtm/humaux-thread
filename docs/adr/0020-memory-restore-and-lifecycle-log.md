# ADR-0020: `memory.restore` 与 memory 生命周期事件日志 —— 撤销一次 SUPERSEDE

日期：2026-09-04 · 状态：Accepted · 影响面：`migrations/0149_memory_lifecycle_events.{sql,manifest.toml}`（新表 `ops.memory_lifecycle_events` + owner SECURITY DEFINER `ops.append_memory_lifecycle` + `private.memory_records.lifecycle_head_event_id` 列与列级 grant）/ `crates/domain/src/{lifecycle.rs（新）,confirm.rs,context.rs,error.rs}` / `crates/adapters/src/{memory_governance_repo.rs,context_repo.rs}` / `bins/gateway/src/{bootstrap.rs,mcp_application.rs,memory.rs,remember.rs}` / `contracts/mcp/{memory.schema.json,memory.output.schema.json}` / `xtask/src/rls_check.rs` / `bins/gateway/tests/mcp_gateway.rs`。无新 `ErrorCode`。

## 背景
仓库里没有任何 lifecycle 迁移是可逆的：`memory.restore` 在 `memory.schema.json` 的 oneOf 里根本不存在，没有 `undo_deadline` 列或计算，唯一的 tombstone 原语（`forget_repo.rs`）由 DB 触发器单向锁死（0011 里没有任何角色有从 `TOMBSTONED` 出发的合法边）。agent 一次误操作就是永久的，这让每一个治理写都更可怕。本卡补 memory 级的撤销：把 SUPERSEDE 变回 active。

## 研究问题 1（事件住哪）
memory 级的 lifecycle 事件哪个既有 sink 都不合适：`projection.stream_log` 是冻结的 12 列 DDL、终态集闭合（§37.1）、且不带 `memory_id`；`ops.outbox` 要求 `evidence_id NOT NULL`。所以新建**追加型**表 `ops.memory_lifecycle_events` 持有转换史，而投影副作用仍**骑既有的 `MEMORY_LIFECYCLE` 票**（`projection.stream_log` 的 ISSUED 行 + `ops.outbox` 行）——卡 1 的 supersede 已经在发这张票，一个机制，不是第二条 `ops.jobs` payload。

## 决定
1. **事件日志（D-A）**：`ops.memory_lifecycle_events`（`event_seq` identity 追加序；`target_kind` MEMORY|CONTRIBUTION_RELEASE；`op` TOMBSTONE|SUPERSEDE|REVOKE|ARCHIVE|RESTORE|ERASE；`reason_code` 可空——只有 RESTORE 为空，撤销的理由在它撤的事件上；`actor_principal_id`；`replacement_memory_id`；`correction_evidence_id`；`undoes_event_id` self-FK；`undo_deadline`；`idempotency_key`；`request_fingerprint`；`stream_seq`/`commit_seq`；`UNIQUE(tenant, actor, idempotency_key)`）。**`memory_id` 无 FK**，所以一条转换记录能熬过它所描述的 memory 的 §37 purge。**写入只经 owner SECURITY DEFINER `ops.append_memory_lifecycle(...)`**（EXECUTE 给 role_gateway；SELECT 给 gateway/retrieval_worker/maintenance；无角色持表级 INSERT/UPDATE/DELETE）——与 `ops.record_deletion_plan_step` 同一 chokepoint。`private.memory_records` 加 `lifecycle_head_event_id`（该 memory 最新事件；无 FK），gateway 在**翻 authority status 的那条 UPDATE 里**用列级 grant 一并写头指针（仲裁 WHERE 子句不变）。**卡 1 的 supersede 现在同事务里也追加一条 SUPERSEDE 事件**并盖 `undo_deadline`；本卡前被 supersede 的行头指针不回填（记录在案）。
2. **`ConflictReason(u16)`（D-B）**：`ErrorCode` 保持冻结 18（§52.1）。一次业务冲突在线上是 `ErrorCode::Conflict`，附加的 `reason` 是 `crates/domain/src/error.rs` 里的透明 newtype——gateway 在 `structuredContent {code:"CONFLICT", reason:<u16>, reason_label:<SCREAMING_SNAKE>}` 里带出。常量：1001 UNDO_WINDOW_EXPIRED / 1002 TARGET_NOT_CURRENT / 1003 ERASE_TERMINAL / 1004 TARGET_ADVANCED / 1101 CANDIDATE_ALREADY_CONFIRMED / 1102 CANDIDATE_EXPIRED / 1201 ALREADY_IN_STATE / 1202 NOT_REVERSIBLE。**不新增第 19 个 `ErrorCode` 变体**（ALL/as_str 闸不动）。因此被拒的 restore 是**成功形状**的结果（`isError:false`，带 reason），与 `confirmation_required` 同一先例——冻结的 error_map 无法在 Err 路径上带 reason。
3. **`restore_allowed`（D-C，纯函数，`domain/src/lifecycle.rs`）**：domain 无时钟，调用方传 `window_expired = now >= undo_deadline`，所以完全可表驱动。判序固定：非可撤销的 head 优先（ERASE ⇒ ERASE_TERMINAL；RESTORE/ARCHIVE/TOMBSTONE/REVOKE ⇒ NOT_REVERSIBLE），SUPERSEDE head 的子序 TARGET_NOT_CURRENT（行已不 superseded）→ TARGET_ADVANCED（后继自己被 superseded/缺失）→ UNDO_WINDOW_EXPIRED；无 head ⇒ TARGET_NOT_CURRENT。这是拿干净 reason 的预检；`UPDATE ... WHERE status='superseded'` 在行锁下仍是唯一仲裁（与 supersede 的 `WHERE status='active'` 同形，并发竞态在此裁决，G59-4 恒真）。
4. **`restore_atomically`（一个事务）**：幂等预检（SELECT 命中同 key+fingerprint 的 RESTORE 事件 ⇒ 直接返回原成功，重建 consistency_token，绝不二次 BMO/consume/mutate；key 不同 fingerprint ⇒ ALREADY_IN_STATE）→ consume token（坏 token = `Conflict`，`isError`）→ 读 head + 可见性（`readable_memory_ids`，不可见 = `NOT_FOUND`）+ `restore_allowed`（拒 ⇒ 返回 reason 并让事务回滚，token 消费一并撤）→ reserve BMO（只在成功路径，拒不计费）→ 发**新** `MEMORY_LIFECYCLE` 票（新 stream_seq，旧 TOMBSTONED/consumed 行永不复活）→ append RESTORE 事件（`undoes_event_id` 指向被撤的 SUPERSEDE）→ 仲裁 UPDATE `status='active', superseded_by=NULL, superseded_at=NULL, lifecycle_head_event_id=新事件`（0 行 = `Conflict`，把票和事件一起回滚）→ 结算 → 返回绑定新 seq 的**新** consistency_token。**RESTORE 本身不可撤**（head 是 RESTORE ⇒ 1202）。
5. **撤销窗口（D-D）**：`HUMAUX_GATEWAY_UNDO_WINDOW_SECONDS`（必填 env，无默认字面量，§78.1）；`undo_deadline` 在 SUPERSEDE 写入时盖（`clock_timestamp() + 窗口`，DB 时钟）。restore 读存下的 deadline，自己不需要窗口值。两条写 lifecycle 的路由（supersede/restore）一起以窗口 config 为开关，未配置则都 `reject_unsupported` fail-closed。
6. **幂等（D-E）**：`idempotency_key = hex(sha256(nonce))`——客户端重试同一次已确认的 restore 会呈同一 token，因此靠 `UNIQUE(tenant, actor, idempotency_key)` 返回原事件而非二次追加。与 supersede 不同（supersede 重放已消费 token = `Conflict`），restore 的重放 = 原成功，所以丢响应后的重试是安全的。
7. **§15.5 读己写（RYW）的答案**：§15.5 只为**前向**写定义 RYW（下界）。restore 前签发的 consistency_token 带的是一个较低的 stream_seq；restore 发了一个**更高**的新 seq。用旧（低）token 做的 recall 其下界早已满足 ⇒ **立即返回**，不阻塞等 restore——RYW 只保证看见到 token 序为止的写，不保证看见之后的。要保证看见被恢复的状态，用 restore 返回的**新** token。旧 token 因此仍严格遵守 §15.5（下界语义），由 `bins/gateway/tests/mcp_gateway.rs::native_gateway_semantic_recall_real_qdrant_pg_and_ryw_acceptance` 实测：拿 restore *之前*一次 remember 签发的（较低 seq）consistency_token，在同一 workspace 流上 supersede+restore（发出更高的新 seq）之后再用它 `recall.search`，断言仍立即返回同样的三条 item、既不阻塞也不被判为「尚未服务」。
8. **`DestructiveOp::MemoryRestore`（复用卡 1 的门，不开第二条 token 路径）**：restore 不是破坏性的，但走同一个 confirm 门（`run_confirmed_write`，`successor_id=None`）。`DestructiveOp::ALL` 长度 3→4。
9. **范围与文档化的天花板**：只做 memory 级。forget/tombstone 仍是终态（§37 forget 路径未接本日志），所以本卡的 restore **只覆盖 SUPERSEDE**（无 head / 非 SUPERSEDE head 均被 `restore_allowed` 拒）。ARCHIVE（卡 4）、correct 的 candidate（卡 5）等在 `LifecycleOp`/`LifecycleReason`/`ConflictReason` 里已留位，本卡不实现。

## 越界改动（需主线裁决，与 ADR-0018/0019 同一情形）
- `crates/domain/src/{confirm.rs,context.rs}`：加 `DestructiveOp::MemoryRestore` 变体是闭合集扩展（confirm.rs 文档本就写「每个被门控的 op 加一个变体」）；`context.rs::from_consumed_confirmation` 的 match 因穷尽性必须加一臂（restore 不是 pin/unpin ⇒ `MissingConfirmation`）。
- `crates/adapters/src/context_repo.rs`：`write_binding` 的 match 因穷尽性加一臂（restore ⇒ `InvalidInput`，它不是 binding 写）。
- `crates/protocol/src/mcp_catalog.rs` 单测：output 联合从 5 支断言改成 7 支（新增 `Restored` / `ConflictReason` 分支）——卡 1/2 同类主线契约。
- `xtask/src/architecture_check.rs`（2 处）与 `bins/gateway/tests/continuity_get.rs`（1 处）的 `SUPPORTED_OPERATION_KEYS: [&str; 9]` needle 机械改成 10——否则 architecture-check 与 continuity_get 必红。

## 验收
`bins/gateway/tests/mcp_gateway.rs::native_mcp_memory_restore_confirm_gate_acceptance`（真 role_gateway LOGIN + 真 PG）：(a) supersede A→B 后窗口内 restore ⇒ A 复 active、`superseded_by` NULL、G59-4 恒真、head 是 RESTORE 且 `undoes_event_id` 指向那条 SUPERSEDE、新票 stream_seq 更高、返回新 consistency_token；(b) 窗口后 restore ⇒ CONFLICT reason 1001、零变更、token 未消费；(c) 后继自身被 superseded ⇒ 1004；(d) head 是 RESTORE ⇒ 1202；(e) 同 token 重放 ⇒ 原成功、只一条 RESTORE 事件；(f) 不可见/不存在 target ⇒ NOT_FOUND；(g) 并发双 restore（窗口锁重叠）⇒ 恰一胜、败者 consume+事件回滚、G59-4 恒真。故障注入：把 head-row UPDATE 与事件 append 拆成两事务本会留孤儿事件——测试用 BEFORE UPDATE 触发器让仲裁 UPDATE 抛错，断言无孤儿 RESTORE 事件、memory 仍 superseded、token 未消费。单测：`humaux-domain --lib`（`restore_allowed` 表驱动 + `ConflictReason` 常量/标签冻结 + lifecycle 三枚举 DB 映射）、`humaux-adapters --lib lifecycle`（restore 输入契约 + 幂等 key = token 摘要）。门：`cargo xtask migrate`（0149 应用、drift 0）/ `rls-check` / `architecture-check` / clippy / fmt / secret grep。real-provider 演练：write → distill → supersede → restore → recall 显示被恢复的 memory。
