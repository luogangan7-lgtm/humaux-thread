# ADR-0018: confirm_token 两步门（§33.10 规则 9）与首个消费者 `memory.supersede`

日期：2026-09-03 · 状态：Accepted · 影响面：`migrations/0148_confirm_tokens.{sql,manifest.toml}` / `crates/domain/src/confirm.rs`（`DestructiveOp`、`ConfirmToken`）/ `crates/application/src/supersede.rs`（铸 token、pair 规则）/ `crates/adapters/src/{confirm_token_repo.rs,memory_governance_repo.rs}` / `bins/gateway/src/{guard.rs,mcp_application.rs,memory.rs,bootstrap.rs}` / `xtask/src/rls_check.rs` / Baseline §6.2.2

## 背景
`memory.supersede` 自 `contracts/mcp/memory.schema.json` 起就是 schema 声明的操作，G59-4 CHECK 与列自 0004 起就在，但全仓没有任何 adapter 写 `superseded_by`，`SUPPORTED_OPERATION_KEYS` 也没有它——agent 今天无法纠正一条写错的 Memory。它和后面每一个治理操作（correct / archive / forget）共用同一个前置条件：§33.10 规则 9 的 `confirm_token` / two-step confirm fallback，而 `crates/domain/src/context.rs` 明写 `ConfirmedUserActor` 全仓零铸造路径。所以门是真正的第一个阻塞点，supersede 是验证它最便宜的真实操作。

## 决定
1. **门是共享的前置条件，不是每个 arm 各写一份。** `GatewayGuard::run_confirmed_write` 走与其它路由相同的 admit（认证 / scope / 网络 / rate / entitlement），然后按 `ConfirmGate.presented` 分叉：
   - 无 token（D-B 第一次调用）：`application::supersede::mint_confirm_token()` 出 32 字节随机 nonce（D-A），`confirm_token_repo::mint_with_audit` 在**一个事务**里写 `control.confirm_tokens`（只存 sha256(nonce)，绑定 tenant/user/operation/target/**successor**——`successor_id` 钉住 `replacement_memory_id`，确认的是「用 B 替换 C」这一对，而不是「替换 C」；同一 token 换成 `(C, E)` 重放是 `CONFLICT`，`expires_at = now + HUMAUX_GATEWAY_CONFIRM_TOKEN_TTL_SECONDS`）+ 该操作的 `MCP_REQUEST_FINISHED` 审计，无其它持久写、不预留 BMO。**该审计带 `risk_tags=[CONFIRMATION_MINTED]`**（§77）：mint 与执行的审计三元组 (action, resource_id, result) 完全相同，没有这个标签审计方无法分辨「申请确认」和「真的写了」；adapter 侧 `validate_mint` 要求它在场、`memory_governance_repo::validate` 要求它缺席，两个方向都钉死。返回 `isError=false` 的正常 MCP 结果：`{"confirmation_required":true,"confirm_token":<base64url>,"operation":<key>,"target":{...},"expires_at":<RFC3339>}`。「需要确认」不是错误（§52.1 的 18 个 `ErrorCode` 不加变体）。
   - 有 token（第二次调用）：门只把 `ConfirmationClaim{op,target,sha256}` 交给 handler；**消费必须发生在 handler 自己的事务里**（`confirm_token_repo::consume_in_txn` 是唯一消费入口，`memory_governance_repo::supersede_atomically` 在 reserve BMO 之后、任何行读取之前调用它）。单条 `UPDATE ... WHERE nonce_sha256 AND tenant AND user AND operation AND target AND successor IS NOT DISTINCT FROM $6 AND consumed_at IS NULL AND expires_at > now RETURNING`（`confirm_token_repo::CONSUME_SQL`，每个子句由 `consume_predicate_is_the_full_binding` 单测钉住——0148 的 owner 触发器自己也拒绝过期消费，所以 live 测试分不清「adapter 拒的」还是「触发器拒的」，adapter 谓词需要自己的见证）：0 行 —— 重放、过期、绑到别的 target / successor / operation / user —— 一律现有 `CONFLICT`（tool error，不做 403 oracle，永不静默成功）。DB 侧 owner 触发器再钉一次单次使用（`consumed_at` 只能 NULL→非 NULL 一次、不得晚于 `expires_at`、其它列不可变）。
2. **闭合类型，无字符串**（§78.2）：`DestructiveOp::{MemorySupersede}` 是被门控操作的闭集，其 `operation_key()` 是 `"memory.supersede"` 这个字面量在仓里唯一的出处；`SUPPORTED_OPERATION_KEYS` 与 `invoke()` 的 dispatch arm 都从它取（D-D），`reject_unsupported` 继续覆盖 `memory.correct/confirm/pin/archive`。`ConfirmToken` 的 wire 形式是无 padding base64url（43 字符，严格解码、非规范尾位拒绝），`Debug` 打码。
3. **supersede 语义（D-C）**：`memory_id`（target）与 `replacement_memory_id`（successor）都必须存在、同租户、对调用者可见（`context_repo::readable_memory_ids`，与 `memory.get` 同一个 `can_read` 判官）；successor 必须 `active`（`application::supersede::check_pair`），自我替换是 `INVALID_INPUT`。**target 的状态不预读**：`UPDATE private.memory_records SET status='superseded', superseded_by=$succ, superseded_at=clock_timestamp() WHERE memory_id=$target AND status='active'` 是 target 状态的唯一判官——G59-4 在新行上成立；0 行 = `CONFLICT`，「已被替换」（验收 (f)）与并发双 supersede（(g)）都由这一个谓词裁决（READ COMMITTED 下 UPDATE 在拿到行锁后重判 `status='active'`）。之前的版本先 SELECT 两行状态再 UPDATE，SELECT 成了第二个判官，把 WHERE 谓词遮成了从不被测试触及的死代码（变异「去掉 status='active'」测试不红）；现在去掉那个谓词 (f) 会成功替换、(g) 会两个都赢，测试立刻红。同一事务内还完成 BMO reserve→CONSUMED、`MCP_QUOTA_RESERVED/CONSUMED`、`MCP_REQUEST_FINISHED`（§34.0.1 的原子形态）；任一步失败整体回滚，token 保持未消费（故障注入：在 memory_records 上装 RAISE 触发器，supersede 失败后 `consumed_at` 仍为 NULL、行仍 active，拆掉触发器同一 token 可成功——若消费与 UPDATE 分两个事务，这个哨兵立刻变红）。0148 把 `role_gateway` 在 `private.memory_records` 的列级 UPDATE 扩到 `(status,superseded_by,superseded_at)`（0011 漏了 §9 的 `superseded_at`），§6.2.2 与 `rls-check` MATRIX 同变更更新。
4. **投影后果（§7/§15）——做了「发票」这一支**（**2026-09-26 更正：本条「用 status='superseded' 重新 upsert 该点」的部分已被 ADR-0049 D-A 取代** —— 卡 18 的投影注册表只绑定 live 源，这条票在卡 18 之后一直 `registry_failed`；现在非 live 的 memory 由 worker 退休其绑定并删点、票落 DONE）：supersede 事务在 target 所在 workspace 的投影流族（gateway bootstrap 的 stream key，即 `memory.get`/`recall` 读 ledger 的同一把 key）上发一张 `MEMORY_LIFECYCLE` 票：`next_commit_seq` → `issue_stream_log_row`（ISSUED）→ `ops.outbox(event_type='MEMORY_LIFECYCLE', evidence_id = target 的 PRIMARY Evidence)`，复用 `adapters::remember` 里 §60 的三个写函数（`MEMORY_LIFECYCLE` 常量自 T3.x 起就为此预留）。投影 worker（`projection_worker::resolve_memory`）不按 `event_type` 过滤，而是经 outbox→memory_evidence→memory_records 解析到同一条 Memory，用它当前的 `status='superseded'` 重新 upsert 该点的 payload，票按既有路径落 `DONE`；distill worker 只认领 `EVIDENCE_ACCEPTED`，不会碰这行 outbox。因此不需要 worker 侧新的 `SKIPPED_BY_POLICY/lifecycle_not_projected` 分支，§15.7 也没有洞：每张票都有行、都会被销。**未做的部分（诚实登记）**：本卡没有跑真 Qdrant 的 worker e2e 去证明「点 payload 的 status 已翻转」，只在 gateway e2e 里断言票（stream_log ISSUED 行 + outbox MEMORY_LIFECYCLE 行）已发；`private_memory_points` 的确定性 point id 含 `memory_records.updated_at`，本 UPDATE 不改 `updated_at`，所以是同一个点被覆盖而非新增一个点。
5. **幂等（§34.0.1）**：同 request + 同 token 重放 = `CONFLICT`（验收 (c)），不写 `control.operation_receipts`——那张表的触发器把 receipt 绑死在 `remember.put` 形状的 Evidence/stream 引用上，复用会伪造引用。效果上 supersede 本身幂等（行已是 superseded）；调用方重试需重新走第一步拿新 token。
6. **配置（§78.1）**：TTL 只来自 `HUMAUX_GATEWAY_CONFIRM_TOKEN_TTL_SECONDS`（bootstrap 注册表必填、无默认字面量、测试 env map 同步）。未配置时 `GatewayMcpApplication.confirm_token_ttl = None`，`memory.supersede` 按既有 `reject_unsupported` 路径 fail closed。
7. **拒绝的替代方案**：(a) 把 token 消费放在门里、mutation 放在 handler 里——两个事务，部分写入窗口，正是故障注入要抓的；(b) 给「需要确认」加新的 `ErrorCode` 变体——§52.1 冻结 18 个；(c) token 绑定不匹配返回 `FORBIDDEN`——protocol 级 403 会成为 token 存在性 oracle，且与「过期/已消费」分裂成两种可观测状态，统一 `CONFLICT`；(d) 让 supersede 不发投影票、留给以后——§15.7 明禁不可名状的空洞，且 recall 会继续命中已被替换的点；(e) 在 `GuardSettings` 上加 TTL 字段——会连带改 `bins/gateway/tests/continuity_get.rs` 等本卡不拥有的构造点，改为 `GatewayMcpApplication::with_confirm_token_ttl`。

## 已知局限 / 升级信号
- ~~`contracts/mcp/memory.output.schema.json` 缺 supersede 两种结果分支~~ **已由主线在同一变更内修复**：schema 新增 `$defs.ConfirmationRequired` 与 `$defs.Superseded` 两个 `oneOf` 分支（`additionalProperties:false`），`memory_supersede` arm 与其它 memory arm 一样先 `self.catalog.validate_output(ToolName::Memory, &value)?` 再 `output(value)`。主线裁定：该文件与 `xtask/src/architecture_check.rs`、`bins/gateway/tests/continuity_get.rs` 的两处 `SUPPORTED_OPERATION_KEYS: [&str; 7]` 钉子都属主线所有的跨卡契约，由主线改，不算实现者越界。
- **越界改动（需主线裁决）**：`xtask/src/architecture_check.rs`（W2 continuity gate，两处 needle）与 `bins/gateway/tests/continuity_get.rs` 都硬编码了 `SUPPORTED_OPERATION_KEYS: [&str; 6]`；本卡按 D-D 把表扩到 7，这两处**不在本卡允许文件内，但已被改成 7**（否则 `architecture-check` 与 `continuity_get` 必红，卡的停止条件无法同时满足）。改动是机械的、由 D-D 强制的；但这意味着 `architecture-check` 对本卡是部分自证的——闸自己的常量被它要管的改动挪了。主线合并前请显式确认这两处，或把它们加进允许清单。
- 只有 `memory.supersede` 走门；`correct / archive / forget` 接入时各加一个 `DestructiveOp` 变体与一个 `run_confirmed_write` 调用，不再需要新的门。

## 验收
`bins/gateway/tests/mcp_gateway.rs::native_mcp_memory_supersede_confirm_gate_acceptance`（真 role_gateway LOGIN + 真 PG）：(a) 无 token 返回 `confirmation_required` + token，行不变；(b) 带 token 一次提交翻转 status/superseded_by/superseded_at 并发出 MEMORY_LIFECYCLE 票；(c) 重放已消费 token → CONFLICT；(d) 过期 token → CONFLICT；(e) 为 (C→B) 铸的 token 对 target D、对 successor E、对另一 operation 绑定、对另一 user 的凭证均 CONFLICT；(b) 的审计断言按 `CONFIRMATION_MINTED` 标签拆成「1 条 mint + 1 条执行」；(f) 再 supersede 已 superseded 的行 → CONFLICT；(g) 两把 token 并发 supersede 同一行，恰一个成功，G59-4 全程成立；故障注入：memory_records 上的 RAISE 触发器让 UPDATE 失败时 token 未被消费、行未变。单测：`humaux-domain --lib confirm`、`humaux-application --lib supersede`、`humaux-adapters --lib confirm_token` / `--lib memory_governance`。门：`cargo xtask migrate` / `rls-check` / `architecture-check` / clippy / fmt / secret grep。
