# ADR-0032: 写路由的 stream identity 按请求推导 + `remember.put` 每次调用可选 visibility_class（Card 11）

日期：2026-09-06 · 状态：Accepted · 影响面：`bins/gateway/src/remember.rs`（`PutClassification`、三个闭集 parser、`command(stream, classification)`）/ `bins/gateway/src/mcp_application.rs`（`remember_put` 经 `ContextBootstrap::request_stream` 推导写流；wire 多三个可选字段）/ `bins/gateway/src/bootstrap.rs`（parser 复用 + key 表注释）/ `crates/adapters/src/operation_receipt.rs`（receipt 键含 stream scope；`TENANT_SHARED_WRITER_ROLES` 成员角色闸）/ `contracts/mcp/remember.schema.json`（`visibility_class` / `data_class` / `event_kind` 可选闭集）/ 迁移 `0158_operation_receipts_stream_scoped_key`（receipt 主键换成 6 列）/ `crates/adapters/src/remember.rs`（`resolve_reasoning_domain`：写事务内按调用方租户解析 reasoning domain；`RememberError::ReasoningDomainUnresolved`，其 1 行映射臂同时落在 `affect_repo.rs` / `distill_repo.rs` / `memory_governance_repo.rs` 的穷举 match 里）/ 迁移 `0159_evidence_reasoning_domain_tenant_fk`（`private.evidence_objects (tenant_id, reasoning_domain_id)` 复合 FK）/ 迁移 `0160_memberships_role_closed_set`（`control.memberships.role` 大写回填 + 写入时规范化触发器 + `OWNER|ADMIN|MEMBER` CHECK）/ Baseline §34.0.1 / 测试 `bins/gateway/tests/mcp_gateway.rs::native_mcp_remember_put_per_call_visibility_and_per_request_stream`（非 ignore，纯 PG）+ `native_mcp_remember_put_p50_speed_record` + ADR-0031 三 pair 测试的 receipt 主键 pin 改为 6 列。前置：卡 1–10 与 E1 在树上（HEAD bcace0f，迁移至 0157）。研究档案：`research/webgpt-spec-silence-rulings-20260903.md` Q9（STREAM IDENTITY / receipts）。

## 背景
ADR-0031 把三条读路由抬到按请求推导的 stream identity，但写路由还绑着 bootstrap 的一条写流：`remember.put` 对配置外的 `(tenant, workspace)` 硬拒 `FORBIDDEN`。写侧还带着第二个产品限制——`visibility_class` 由 `HUMAUX_GATEWAY_REMEMBER_VISIBILITY_CLASS` 一次定死，`TENANT_SHARED` 在 `RememberPolicy::new` 处被硬拒：一个部署放不下「一条私密笔记 + 一条 workspace 共享笔记」。两个常量都在 `RememberPolicy` 上，分开改会碰同一段代码两次，所以一张卡一起处理。

## 决定

### D-A 写流按请求推导，与读路由共用同一推导点
- `remember_put` 在 `run_atomic_remember` 的 prepare 闭包里调 `ContextBootstrap::request_stream(principal tenant, requested workspace)` —— 与 `memory.get/enumerate`、`recall.search`、`context.assemble` **同一个函数**（ADR-0031 D-A 的唯一推导点），不再比对 `REMEMBER_TENANT_ID / WORKSPACE_ID`。纯函数，零 PG 往返。
- 请求 workspace 由 guard 的 `credential.authorize → narrow` 收窄（非成员 ⇒ `FORBIDDEN`，早于任何写）；`remember::command` 再复核 stream 落在 `AuthorizationScope` 内（进程内调用方的纵深防御）。
- **写不经 serving 读**：读需要 pair 已 provision（§16.2 serving 行）才不会读到合成空账本；写恰好相反——某个 pair 的第一次写入就是它存在的证明。checkpoint 行由 `issue_stream_log_row` 的 `INSERT … ON CONFLICT DO NOTHING` 按 family 幂等创建（既有代码，卡 11 不改 adapter 的写事务），随后 `issued_highwater + 1`、stream_log 行、outbox 票——验收测试断言 pair B 的第一次写入使其账本从 `(0,0,0)` 变 `(1,1,1)` 而 pair A 的账本只数自己的写。
- **reasoning domain 随调用方租户，不随进程**（评审 P0 修正）。`HUMAUX_GATEWAY_REMEMBER_REASONING_DOMAIN_ID` 是 bootstrap 租户的一个 `control.private_reasoning_domains` 行；写流抬到按请求推导后，若仍把它原样盖到租户 B 的 Evidence 上，B 的行会持有一条指向 A 控制面数据的活指针（0004 的单列 FK 不看 tenant，RI 检查绕过 RLS，没有任何东西拦），且 B 自己的 domain-scoped 管线（consolidate / contribution 都按 `eo.reasoning_domain_id` 过滤）永远看不到它。修正分两层，缺一不可：
  - **写事务内按租户解析**：`adapters::remember::remember_in_txn` 在首个写之前调 `resolve_reasoning_domain`（Evidence 的唯一 INSERT 缝，`remember.put` / 批次 / confirm / correct 都经它）：一条索引读，在该租户的 RLS 之下——① 进程配置的 domain 若属于**本租户**且 ACTIVE 则原样使用（部署自己的租户字节不变，private worker 蒸馏的正是它）；② 否则取 on-behalf-of user 拥有的 ACTIVE domain（§11.2.1 Ingress「用户直接输入 → 该用户」）；③ 都没有 ⇒ `ReasoningDomainUnresolved` → `DEPENDENCY_UNAVAILABLE`，未写（§11.2.1「无法确定 processing principal」：这个租户还没被 provision 到能写）。
  - **数据库自己拒绝跨租户 domain**：迁移 0159 给 `private.evidence_objects` 加 `(tenant_id, reasoning_domain_id)` 复合 FK（0131 已给目标表加了同形 UNIQUE；与 `contribution_executions_domain_fk` 同一形状）。绕过解析的写入是 `23503`，不是静默的跨租户指针。0004 的单列 FK 保留。
  - `remember::command` 里 `stream.tenant_id != authorization.tenant_id()` 这条守卫在 HTTP 路由上按构造恒假（stream 就是从 authorization 推导的），它只是进程内调用方的纵深防御，**不是**写路由的租户钉；租户钉是数据库的。
- `HUMAUX_GATEWAY_REMEMBER_TENANT_ID / WORKSPACE_ID` **保留**，用途缩为两个：调用未带 `workspace_id` 时的缺省 pair（向后兼容：老调用方一字不改）；confirm-gated 治理动词（`memory.supersede/restore/archive/…`、`subject_register/link_key`、`annotate_affect`）仍经 `memory::write_scope` / `run_confirmed_write` 常量比对——那些路由在 `bins/gateway/src/memory.rs`，不在本卡允许面内，抬它们是下一张卡（见「否决/未做」）。

### D-B `visibility_class` / `data_class` / `event_kind` 每次调用可选，闭集内，只能收窄
- schema 加三个可选 enum 字段；缺省 = 进程 env（`HUMAUX_GATEWAY_REMEMBER_{VISIBILITY_CLASS,DATA_CLASS,EVENT_KIND}`）。三个 parser（`remember::parse_visibility_class` / `parse_data_class` / `RememberEventKind::parse`）同时被 bootstrap 与 wire 使用——env 拼写与 wire 拼写不可能分叉（§78.2）。schema 之外的值在 catalog 处 400 `INVALID_INPUT`，未进 dispatch。
- 收窄规则（§6.1.1「MCP 参数只能缩小 scope」）：`USER_PRIVATE` 绑 on-behalf-of user（无 user ⇒ `FORBIDDEN`，既有）；`WORKSPACE_SHARED` 绑已收窄的请求 workspace（= 推导出的 stream 的 scope_id）；`TENANT_SHARED` 绑 NULL/NULL。
- **`TENANT_SHARED` 变为可达，但只对 `control.memberships.role ∈ {OWNER, ADMIN}` 且 `state='ACTIVE'` 的成员**（`operation_receipt::TENANT_SHARED_WRITER_ROLES`，§78.2 闭集只在读它的那条语句旁定义一次）。为什么按角色而不是按 credential scope：`memory:write` 是每个成员都有的 scope，租户级受众是最宽的一档，让任意成员用一次调用把内容广播给整个租户等于把 §6.1.1 的可见性分层降级成 tenant 隔离；成员角色是仓库里现成的、可审计的授权轴（Baseline §6.1.1 `TENANT_SHARED -> principal 有 tenant read permission`、`last OWNER cannot silently leave` 已把 OWNER 定为租户级权限的持有者）。判定放在 receipt 事务内（`remember_atomically`，receipt miss 之后、reserve 之前）：只有请求 `TENANT_SHARED` 时才多一次索引读，拒绝时无 Evidence、无 BMO、无 receipt（验收测试用 durable counts 钉住）；返回 `INVALID_INPUT`（卡片裁决），wire 上是 §52 的 invalid-params 400。
- 进程缺省不允许 `TENANT_SHARED`（bootstrap 的 `visibility()` 仍只收两值）：缺省是「未声明时的落点」，租户级受众必须是显式声明。
- **`role` 列先闭集再比对**（评审 P1 修正）。0003 的 `control.memberships.role` 是无 CHECK 的自由文本，树里四种拼写（`member`×11 / `OWNER`×7 / `MEMBER` / `owner`）；对它做精确匹配的授权闸，对任何别的拼写都是静默拒绝——这是系统里第一条按角色的授权判定（此前所有成员检查只看 `state`），不能落在开放列上。迁移 0160：① 回填 `role = upper(role)`（只改拼写，不改任何人的角色）；② `memberships_canonical_role` BEFORE INSERT/UPDATE OF role 触发器把每次写入折成大写——老 seed 的 `'owner'` 落库即 `OWNER`；③ `memberships_role_known` CHECK `role IN ('OWNER','ADMIN','MEMBER')` 关闭集合，扩集是新迁移。`TENANT_SHARED_WRITER_ROLES` 于是是闭集里的两个值而不是对自由文本的猜测。为什么不在读侧 `upper(role) = ANY(...)`：那只让这一个读者容错，列仍然开放，下一个读者照样错。闸同时要求 `users.state='ACTIVE'` 与 `tenants.state='ACTIVE'`（与 `contribution_entry_repo` 的 §6.3 三元组一致），此前只看 membership state。

### D-C receipt 键含 stream scope（迁移 0158）
- 主键从 `(tenant_id, principal_id, operation, idempotency_key)` 换成 `(tenant_id, principal_id, scope_kind, scope_id, operation, idempotency_key)`；advisory lock 串与 receipt 查找同步带上 scope；`projection_version` 仍只是 payload 列（Q9：serving 切换不得重开已提交的键）。`principal_id` 就是 credential（api_key_id），卡片文字里的「client」即它，没有第二个 client 标识。
- 语义：同一 principal 在两条流上复用同一 `idempotency_key` 是两次操作；两条流上并发的同键写入各自拿各自的 advisory lock，不互相串行。既有的同键同流并发保护（`concurrent_same_key_never_commits_two_business_or_bmo_rows`）与同键异字节 `CONFLICT` 不变。
- 为什么不是应用层拼 key（把 scope 编进 `idempotency_key` 列）：列有 128 字符 CHECK，uuid+key 放不下；哈希化会让 receipt 行失去调用方原键（审计不可读）；spec 与裁决的用词是键的列，不是列的编码。
- ADR-0031 用 `pg_constraint` 钉的 4 列 pin 改为 6 列；去掉 `tenant_id` 或加进 `projection_version` 仍红。

## 验收 gate
`native_mcp_remember_put_per_call_visibility_and_per_request_stream`（非 ignore，纯 PG，与 replay/ack-loss 验收同一 fixture）：一个进程（bootstrap 写 pair = A）——同一 session 三次 `remember.put` 落 `USER_PRIVATE(user, NULL, PRIVATE, MANUAL_NOTE)` / `WORKSPACE_SHARED(NULL, A, INTERNAL, USER_MESSAGE)` / 缺省 = env；member 请求 `TENANT_SHARED` ⇒ 400 `INVALID_INPUT` 且 durable counts 不变；`EVERYONE` ⇒ 400（schema）；升为 OWNER 后 `TENANT_SHARED` 落 `(NULL, NULL)`；升为 owner 用的是小写 `'owner'`（落库读回 `OWNER`；改成 `'viewer'` 是 CHECK 违例）；同租户第二个 workspace B 的凭据写入 ⇒ B 的账本 `(0,0,0)→(1,1,1)`（checkpoint 行由这次写创建、票发在 B 上），A 的账本 `(4,4,4)`；A 凭据指名 B ⇒ 403 `FORBIDDEN`；**另一个租户 C**（嵌套第二个 fixture，同一进程）：C 的 fixture domain 既不是进程配置的也没有 owner ⇒ 200 tool error `DEPENDENCY_UNAVAILABLE`、durable counts 不变、C 账本 `(0,0,0)`；把 C 的 domain 绑到 C 的 user 后再写 ⇒ 落 C 的流（账本 `(1,1,1)`），`reasoning_domain_id` = C 自己的 domain（≠ 进程的 boot 常量），A/B 账本不变；owner 客户端（绕过 RLS）直接 INSERT 一条「租户 A + C 的 domain」的 Evidence ⇒ `23503`（0159 复合 FK）；C 凭据指名 A 的 workspace ⇒ 403 `FORBIDDEN`；同一 principal（双 workspace scope）同一 `idempotency_key` 在 A、B 两条流上**并发** `remember_atomically` ⇒ 两次 committed、两个 Evidence、两行 receipt，各流各自 replay 回自己的 Evidence；末尾 9 次 put 记 p50。既有 `native_mcp_gateway_real_auth_atomic_replay_and_fail_closed_acceptance`、`native_mcp_gateway_commit_ack_loss_is_unknown_and_replays_the_committed_receipt` 继续通过；ADR-0031 三 pair 测试（`--ignored`）的 6 列 pin 通过。
故障注入实测（2026-09-06，`scratchpad/gates11/fi_card11_drop_scope.{patch,log}`）：从 advisory lock 串与 receipt 查找里去掉 `scope_kind/scope_id` ⇒ 并发分支 `same key on stream B commits concurrently, never CONFLICT: Conflict`，红；恢复后绿。

真实 provider 演练（2026-09-06，`scratchpad/gates11/rehearse_card11.sh` + `recall_user2.sh`，日志 `scratchpad/gates11/e2e_card11/rehearsal.log`；真 MiniMax distill + 真 DashScope 投影/查询 embedding，本机 gateway / retrieval-worker / private-worker 三进程，Qdrant 6333）：同一 session、同一 OWNER 凭据两次 `remember.put`——`visibility_class=USER_PRIVATE` 与 `WORKSPACE_SHARED`——Evidence 落 `USER_PRIVATE/<user1>/-`、`WORKSPACE_SHARED/-/<ws>`；distill 出的两条 memory 继承各自的 visibility；两张票 `1:DONE, 2:DONE`，2 个投影点，`projection-serve` 切 v1 serving；recall：user1（OWNER，两条都在其 scope）两问各命中（rust_hits=4 / health_hits=4）；user2（同 workspace 的 plain member，自己的凭据）只拿到 WORKSPACE_SHARED 那条（`memory_id …ab35`），对「which language」的问句 rust_hits=0——USER_PRIVATE 的记忆没有越过 user 边界。

## 速度
推导是纯函数。写事务内新增**一次**索引读（`resolve_reasoning_domain`：主键/`(tenant_id, reasoning_domain_id)` UNIQUE 命中，每次 put 都跑——这是「一个进程服务 N 个租户」本身需要的那一次，不是可省的）；`TENANT_SHARED` 路径再多一次 `memberships` 读（只在该路径）。实测 p50（同机同库，n=9/次；日志 `scratchpad/gates11/p50_{before,after}.log`、`p50_after_reruns.log`、`card11_after.log`）：`remember.put` plain shape 改前 18.8 ms（1 次）→ 改后 22.2 / 23.4 / 25.3 ms（3 次，中位 23.4）；带 `visibility_class` 的调用（同一进程、同一路径多三个 Option 解析）18.8 / 19.5 ms。改后各次之间的离散（18.8–25.3）大于「改前 vs 改后」之差，且改后三次都跑在 23 分钟全量 clippy 之后的同一台机器上；代码层面 plain 路径没有新增任何 PG 往返（receipt 查找仍走主键索引、推导是纯函数），`TENANT_SHARED` 路径多一次 `memberships` 索引读。

## 否决 / 未做（本卡面内明说）
- **把写路由钉回 bootstrap 租户**（评审给出的另一个选项：`stream.tenant_id != policy.stream.tenant_id ⇒ FORBIDDEN`）：能堵住跨租户 domain，但卡片验收明写「两个不同 (tenant, workspace) pair 落到各自的流」，钉回去等于宣布本卡只做了半个多租户；解析 + 复合 FK 用同样多的代码把两件事都做对。
- **读侧大小写不敏感比对 `upper(role)`**：见 D-B；列不闭合，问题只是换了个读者再现。
- **`RememberCommand.reasoning_domain_id` 改成 `Option`**：会碰所有构造它的测试与 fixture（不在本卡面内），而语义上进程配置值仍是合法缺省，`Uuid` 不变、事务内重解析更省。
- **应用层把 scope 编进 `idempotency_key`**：见 D-C。
- **`TENANT_SHARED` 按 credential scope（新 scope `memory:write:tenant`）而非成员角色**：要改 credential scope 闭集、seed、guard，且和成员角色形成两套授权轴；角色轴已存在且本身就是租户级权限的载体。若日后要让 service credential（无 user）写 `TENANT_SHARED`，再加 scope——今天无 user 的 put 本来就 `FORBIDDEN`。
- **移除 `REMEMBER_TENANT_ID / WORKSPACE_ID`**：治理动词的 `write_scope` 常量比对在 `memory.rs`（本卡不可改），且它们是无 `workspace_id` 调用的缺省 pair；等治理动词抬到按请求推导时一并处理。
- **写路由也经 serving 读**：写就是 pair 存在的证明，再加一次 PG 往返只换来「未 provision 的 pair 不能被写」——而 provisioning（`xtask projection-serve`）本来就是读侧的事。
- **一个 credential 跨多个 workspace 的 HTTP 级同键测试**：credential 今天恰绑一个 workspace（`BoundedSet::new(Option)`），HTTP 上一 principal 只能到一条流；D-C 的并发分支因此直接打 `remember_atomically`（双 workspace scope）——那正是键要保护的形状，等多 workspace credential 出现时它已经是绿的。
