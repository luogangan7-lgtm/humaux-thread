# ADR-0019: `memory.pin` / `memory.unpin` 走 confirm_token 门 —— PINNED 的唯一铸造路径与幂等

日期：2026-09-04 · 状态：Accepted · 影响面：`crates/domain/src/{confirm.rs,context.rs}` / `crates/domain/tests/{context_authorize.rs,ui/fail_confirmed_user_actor_literal.rs}` / `crates/application/src/pin.rs` / `crates/adapters/src/context_repo.rs`（`insert_binding_in_txn` / `revoke_binding_in_txn` 拆出，池版 `insert_binding` / `revoke_binding` 签名不变、变薄壳）/ `xtask/src/architecture_check.rs`（A3 加 `from_consumed_confirmation(` needle）/ `bins/gateway/src/{mcp_application.rs,memory.rs}` / `contracts/mcp/memory.schema.json` / `contracts/mcp/memory.output.schema.json` / `bins/gateway/tests/mcp_gateway.rs`。无迁移、无新表、无新 `ErrorCode`。

## 背景
PINNED binding 是 agent 让一条 Memory 在**每次** context assembly 里存活的唯一手段。读侧早已闭环（`context_repo::PinnedLane` → `context.assemble` / `continuity.get`），写侧代码齐全却不可调用：`insert_binding` 只收私有字段的 `BindingGrant`，而能造出它的 `authorize_pinned` 需要一个 `ConfirmedUserActor`——该类型刻意零构造路径（spec :6062-6070：没有 confirm_token/MRTR 就接 pin = 授权绕过攻击）。ADR-0018 把门造好了，本卡接第二个消费者。

## 决定
1. **actor 的铸造点（D-A）**：`ConfirmedUserActor::from_consumed_confirmation(op, memory_id)` 是唯一构造式，只认 `DestructiveOp::{MemoryPin, MemoryUnpin}`（supersede 的确认不是 pin 的确认），并**绑定一条 memory**：`authorize_pinned` 现在比对 `actor.memory_id() == req.memory_id`，拿 X 的确认建 Y 的 binding ⇒ `MissingConfirmation`。调用它的唯一生产代码是 `context_repo::write_binding_confirmed`，且**发生在 `confirm_token_repo::consume_in_txn` 成功之后、同一事务里**（0 行 = `CONFLICT`，永远到不了铸造）。`tests/ui/fail_confirmed_user_actor_literal.rs`（trybuild，夹具 `crates/domain/tests/context_authorize.rs`——路径正是 architecture-check A3 早已白名单的那个）注错证明字面量构造不编译。**诚实边界**：Rust 可见性表达不出「只有 gateway 能调 pub fn」——`from_consumed_confirmation` 的入参（一个枚举值、一个 uuid）任何 crate 都造得出。把路径钉死的是 architecture-check A2/A3 三条 needle：`BindingGrant {` 只许在 domain、`authorize_pinned(` 与 **`from_consumed_confirmation(`** 只许在 domain 定义处与 `context_repo`（评审裁决后加入 A3），而 context_repo 的唯一调用点在 consume 之后。注错 UI 测试证明的只是字面量构造不编译；「不能调铸造函数」由 A3 证明，不由 UI 测试证明。MANDATORY 不变：`ElevatedActor` 仍无构造式。
2. **写路径（D-B）**：`context_repo::pin_confirmed` / `unpin_confirmed` 共用一个信封 `write_binding_confirmed`，与 `memory_governance_repo::supersede_atomically` 同形：reserve BMO → `MCP_QUOTA_RESERVED` 审计 → **consume token** → 可见性（`readable_memory_ids`，与 `memory.get` 同一个 `can_read` 判官；不可见 = `NOT_FOUND`）→ 找 (tenant, WORKSPACE=绑定 workspace, memory) 的活 PINNED 行 → 写 binding → 量消费 → 审计 → COMMIT。binding 写本身走**既有且唯一**的两个写入点，拆成 `insert_binding_in_txn` / `revoke_binding_in_txn` **在信封事务上执行**（评审裁决：初版让它们各开自己的短事务，信封在 binding 之后还有三条回滚路径——reservation 非 `Consumed`、finalize 时 lease 已过期、COMMIT 失败——每一条都会留下「行已改、token 未消费、无 OK 审计」；且信封持有池连接 + quota 行锁时再向同一池要第二条连接，默认 `max_connections=10` 下同租户 10 并发就是池耗尽死锁）。池版 `insert_binding` / `revoke_binding` 签名不变，退化为「开事务 → SET LOCAL tenant → in_txn → COMMIT」薄壳，非门控调用方（夹具、`mandatory_context_lane`）不受影响。信封只用一条连接，与 `supersede_atomically` 同形；token 先消费再写行，任何一步失败整体回滚。e2e 见证：owner 持 PINNED 行的 `FOR UPDATE` 锁，直接调 `unpin_confirmed`（1s lease）——信封的 revoke UPDATE 在锁上等过 lease，放锁后 revoke 落下、finalize 判 `Released` 非 `Consumed` ⇒ `CONFLICT`，PINNED 行仍活、token 未消费；把 revoke 换回自开连接（故障注入已实跑）该断言即红（行已撤）。
3. **幂等（D-C）**：`application::pin::pin_action` —— 已钉 ⇒ 返回既有 `binding_id`、`inserted=false`、不插行（唯一索引 `ux_context_bindings_active` 永远不会被同 scope 同 memory 第二次命中）；`unpin_target` —— 无活 PINNED 行 ⇒ 既有 `CONFLICT`。同租户的门控写在 quota window 行锁上串行化（ADR-0018 (g) 的同一机制），所以「先查再插」不会与并发 pin 竞态。
4. **unpin 只撤 binding**（§36 :8572）：`revoke_binding` 是 `UPDATE ... SET revoked_at = now()` 软删；e2e 以 `memory_records` / `memory_evidence` / `evidence_objects` 的 `xmin` 前后相等作证，Evidence/Memory 一行未碰。撤销后 `ACTIVE_NO_AUTO_MUTATE_BINDING` 谓词随之解除，consolidation 重新把它选为输入。
5. **闭合类型与 wire（D-D）**：`DestructiveOp::{MemoryPin, MemoryUnpin}`（`ALL` 长度 3），`SUPPORTED_OPERATION_KEYS` 扩到 9，两条 dispatch arm 共用一个 `memory_binding_write(op)`（wire 形状完全相同：`memory_id` + 可选 `confirm_token`，token 绑定 op —— pin 的确认不能执行 unpin，e2e 钉住）。`memory.schema.json` pin 分支补 `confirm_token`、新增 `unpin` 分支（`memory:write`）。`memory.output.schema.json`：`ConfirmationRequired.operation` 枚举扩到三个、`target.replacement_memory_id` 改为可选，新增 `BindingWritten` 分支；两种结果都过 `catalog.validate_output`。
6. **未做 / 拒绝**：(a) 新增 `authorize_pin` / `authorize_unpin` 函数名——`authorize_pinned` 已经是 PINNED 的唯一入口且被 A3 钉住，再起一个名字就是第二个不受闸管的入口；unpin 撤的是 `binding_id`，不需要 grant，门就是被消费的 token。(b) 复用 `memory_governance_repo` 的信封——它不在允许文件内，且 D-B 要求写入点在 context_repo；信封 ~60 行同形复制，主线若想收敛可抽 `confirmed_write_envelope(pool, auth, op, |txn| ...)`。(c) 给 pin 发投影票——binding 不改 Memory 状态、不影响点 payload，§15.7 无洞。(d) TENANT 档 scope——路由是 credential 绑定的 workspace（与 `memory.get`/`supersede` 同规则），PinnedLane 通过 `scope_chain` 读回同一层。

## 验收
`bins/gateway/tests/mcp_gateway.rs::native_mcp_memory_pin_unpin_confirm_gate_acceptance`（真 role_gateway LOGIN + 真 PG + 真 role_consolidation_worker LOGIN）：基线 Context 无 pinned、consolidation 选得到 x；(a) 无 token ⇒ `confirmation_required`，无 binding 行，除 token 行外零持久写；负例：为 y 铸的 token 用在 x、pin 的 token 用于 unpin、43 位垃圾 token ⇒ 全部 `CONFLICT`、零行、token 未消费（**故障注入已实跑**：把 `consume_in_txn` 的结果丢掉 ⇒ 负例第一条即红，`pin_test_mutant.log`）；(b) 带 token ⇒ 恰一行 `mode=PINNED, scope=WORKSPACE, created_by=user, revoked_at IS NULL`，token 已消费，审计 = 2 条 mint(tag) + 1 条执行，`context.assemble` 的 `handoff.pinned` 只含 x（读侧零改动），consolidation 选不到 x；(c) 第二次确认 pin ⇒ 同 `binding_id`、`inserted=false`、仍 1 行；(d) unpin ⇒ 同一行 `revoked_at` 置位，Memory/Evidence 的 xmin 前后相等，Context pinned 清空，consolidation 重新选到 x；(e) 对未钉的 memory unpin ⇒ `CONFLICT` 且 token 未消费；(c′) 信封回滚见证：owner 行锁把 revoke 拖过 1s lease 后直接调 `context_repo::unpin_confirmed` ⇒ `CONFLICT`，行仍 `revoked_at IS NULL`、token 未消费（binding 写与信封同事务；故障注入：revoke 自开连接 ⇒ 红）；A3 needle 故障注入：生产代码里放一个 `from_consumed_confirmation(` 字面 ⇒ `architecture-check` 红；(f) 重放已消费 token ⇒ `CONFLICT`。单测：`humaux-domain --lib context`（actor 只从 pin/unpin 铸、只对绑定的 memory 有效）、`humaux-domain --test context_authorize`（注错）、`humaux-application --lib pin`。门：`cargo xtask migrate` / `rls-check` / `architecture-check` / clippy / fmt / secret grep。
